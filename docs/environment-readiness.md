# Local and preview environment readiness

This guide sets up a reproducible environment for credential sign-in, the
synthetic demo company and ordinary browser/API checks. The configuration
check does not establish accounting readiness or contact a database/provider.

## Check the intended environment

Run from the repository root:

```bash
npm run env:check -- --help
npm run env:check -- --local
npm run env:check -- --preview
```

Choose one mode. Local loads `.env.local` when present; injected environment
values take precedence. Preview reads only the process environment injected
by the preview platform or an approved secret workflow. It never loads
`.env.local`, pulls remote secrets, writes files, or calls a service. Do not
pass configuration values as command arguments. Errors identify variable
names without printing their values, URLs, passwords or tokens.

Exit code `0` means the required configuration checks passed, `1` means a
configuration/read error, and `2` means invalid command usage. This is a
separate operator command: `build` and `check` do not require runtime secrets
or run it automatically. A build passing is not evidence that auth works.

## Required demo configuration

| Variable | Local | Preview |
| --- | --- | --- |
| `NEXT_PUBLIC_APP_URL` | The browser origin, such as `http://localhost:3000` | The canonical HTTPS preview origin |
| `AUTH_URL` | The same origin as `NEXT_PUBLIC_APP_URL` | The same canonical HTTPS origin |
| `AUTH_SECRET` | An independent local secret generated by `npm run dev:secrets` | A separate server-only Preview secret generated from at least 32 random bytes |
| `DATABASE_RUNTIME_URL` | A restricted application login to the isolated local/test database | A restricted application login to the isolated preview database |

Use origin-only URLs: no user/password, path, query or fragment. A trailing
slash is accepted. HTTP is allowed only for local loopback hosts. Preview
rejects HTTP and loopback origins. Keep `AUTH_REQUIRE_EMAIL_VERIFICATION=true`
(the application default); demo provisioning creates a verified identity.

Auth.js can otherwise infer its origin from proxy headers or legacy
`NEXTAUTH_URL`. This checker deliberately requires an explicit `AUTH_URL`
to make testing reproducible. Remove conflicting `NEXTAUTH_URL` settings.
On Vercel, Auth.js already recognizes platform host trust; setting
`AUTH_TRUST_HOST` is not a substitute for correct origins. Supplying only
`VERCEL_URL` does not configure `NEXT_PUBLIC_APP_URL` or this check.

Use one stable preview alias for both configured URLs and all browser tests.
The cookie API guard compares the browser Origin to `NEXT_PUBLIC_APP_URL`
exactly, while Auth.js uses `AUTH_URL` for redirects. Mixing a generated
deployment hostname with the canonical alias can lose the host-scoped auth
cookie on redirect or make subsequent mutations fail. Keep the same Preview
auth secret across redeployments; changing it invalidates existing sessions.

The checker rejects short secrets and known server credentials configured
under `NEXT_PUBLIC_` names. It cannot prove secret randomness or detect every
possible client exposure. Generate independent values in the intended
environment's secret workflow; do not copy production secrets into Preview.
After changing deployment variables, redeploy so the build/runtime uses them.

## Prepare the isolated database and demo

Use a dedicated empty test database with synthetic data. Keep owner
credentials in setup tooling, outside the deployed web runtime. The migration
runner creates the `ams_runtime` grant role with `NOLOGIN`; creating that role
alone does not provision a restricted application login or its password.
Provision the application login separately with the reviewed grants and use
its URL in `DATABASE_RUNTIME_URL`.

Both setup commands use `MIGRATION_DATABASE_URL` if it is defined, otherwise
`DATABASE_URL`. An explicitly empty override fails instead of selecting the
fallback database. `DATABASE_RUNTIME_URL` is never a setup-owner fallback.
Check the target through trusted database administration before supplying
credentials; the environment checker does not contact or identify it.

```bash
npm run db:migrate
npm run demo:provision
```

Run both commands in the same controlled setup environment against the
isolated owner target. Demo provisioning also loads `.env.local`, so inject
the explicit isolated owner override when invoking it from a developer
checkout. Do not copy an owner URL into the application's runtime variable.
When both are supplied, the checker detects an obvious same-host/database/login
collision; it cannot prove grants or recognize all provider alias equivalences.

The demo follows the normal Credentials sign-in path and needs the migrated
identity tables, a verified user and its synthetic company membership.
Provisioning checks that the public demo identity has no other active company
membership. It also directly activates its synthetic company. Use a newly
created onboarding company to verify the real activation journey; a working
demo does not verify that transition. Never seed shared demo credentials into
production or a database containing customer books.

## Optional services have separate acceptance checks

| Journey | Additional configuration |
| --- | --- |
| Signup, verification and password recovery | `SMTP_URL` and `SMTP_FROM` together; use a sandbox mail destination/provider for Preview |
| Outbox, reminder and export workers | `DATABASE_WORKER_URL` using the restricted worker login, the endpoint's `OUTBOX_WORKER_SECRET` or `EXPORT_WORKER_SECRET`, and the services needed by the queued task |
| Invitation issuance/delivery | Server-only `INVITATION_DELIVERY_KEY` and its delivery configuration |
| Private attachments and scanning | Private object-store/workload credentials, `ATTACHMENT_SCAN_WORKER_SECRET`, `CLAMAV_HOST`, and `CLAMAV_PORT` |

Missing or partial SMTP configuration does not fail this demo-auth check;
the output explains that email delivery remains unverified. With
`NODE_ENV=development`, local email previews use private ignored files.
Preview builds run outside development and require SMTP for email delivery.
The generic “check your email” response does not prove mail was sent.
Workers and attachment services are not validated by this command. See the
main README and each endpoint's configuration before testing those journeys.

## Runtime acceptance after the configuration check

1. Confirm `/api/auth/session` responds normally without `MissingSecret`.
2. Open the canonical preview origin, use the demo sign-in form and confirm
   the same HTTPS origin remains in the address bar through `/companies`.
3. Confirm the session cookie is Secure and HttpOnly. Select the synthetic
   company, create/save one reversible draft and confirm the matching-origin
   request succeeds. Foreign or absent origins must remain rejected.
4. Sign out and confirm the previous session no longer opens private data.
5. Test signup/recovery separately against sandbox mail, and activation with
   a separate newly created onboarding company.

If navigation is blocked by a browser URL/protocol policy, keep that control
intact. Inspect permitted server diagnostics and only sanitized redirect
scheme/host/path information; never dump cookies, tokens or raw auth headers.
Configuration checks cannot establish what the browser actually received.
